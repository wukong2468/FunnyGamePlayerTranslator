# FunnyGamePlayer 文本翻译工具

基于 **Tauri 2 + Rust + React 19 + TypeScript + Material UI** 的游戏文本汉化工具。

读取 FunnyGamePlayer 导出的 `FunnyGameTranslations.json`，自动收集术语表，并通过任意兼容 OpenAI API 协议的接口批量翻译文本，最终导出可直接回填游戏的 JSON 文件。

## 一、核心功能

### 1. 欢迎界面

- 支持通过系统文件选择器选择 JSON 文件，也支持将文件拖入应用窗口。
- 自动解析 `FunnyGameTranslations.json`，校验文件结构，并展示文件基本信息。
- 根据文件路径和文件名识别已有项目，自动加载本地工作区并恢复上次的执行进度。
- 提供最近项目列表，支持重新打开已有项目。
- 对文件格式错误、重复导入、读取失败等情况提供明确的错误提示。

### 2. 翻译配置

- 支持选择源语言和目标语言。
- 展示源文件的分组数量、文本条目数量、字符数、已翻译数量等统计信息。
- 支持导入、导出参考术语表，并在正式翻译前检查相关配置。
- 提供开始术语表收集、进入翻译任务等操作入口。
- 未加载项目时，禁用依赖项目数据的操作，并明确提示原因。

### 3. 术语表收集

- 按原始文本分组，调用 AI 接口并发抽取人名、地名、道具名、技能名、组织名等专有名词。
- 支持开始、暂停或中断、继续执行、从头执行。
- 实时展示总进度、已完成分组、成功数量、失败数量、当前并发状态及运行日志。
- 支持搜索、筛选、分页查看术语。
- 支持新增、编辑、删除术语，并允许修改原文、译文和备注。
- 支持导入和导出术语表 JSON。
- 对重复术语提供明确的合并策略，避免覆盖已有人工校对结果。
- 术语表修改后自动保存到当前项目工作区。

### 4. 翻译任务

- 根据单批字符上限和单批条目上限自动划分翻译批次。
- 支持多批次并发请求，并遵守配置的并发上限。
- 将当前批次命中的术语注入提示词，保证专有名词译名统一。
- 实时展示总体进度、成功数量、失败数量、待处理数量、当前批次及运行日志。
- 支持开始、中断、继续执行、从头执行。
- 继续执行时跳过已完成条目，优先处理待处理或失败条目。
- 从头执行时保留旧译文作为参考，交由模型重新翻译；旧译文不得被误认为本次任务已经完成。
- 支持查看、搜索、筛选、分页浏览原文和译文。
- 支持单条译文手动编辑，并自动保存。
- 支持导入译文并校验条目对应关系，避免因分组、顺序或数据结构不匹配而错误覆盖。
- 支持导出与源文件结构完全一致的 JSON。

### 5. 全局设置

#### 外观设置

- 主题模式：浅色、深色、跟随系统。
- 主题色：允许用户选择主色，并统一应用于 Material UI 主题。
- 密度模式：舒适、紧凑。
- 字体与字体大小：提供合理的默认值，保证长文本、代码片段和日志的可读性。
- 设置修改后立即预览并生效，重启应用后保持不变。

#### AI 接口设置

- API Base URL。
- API Key。
- 模型名称。
- Temperature。
- 请求超时。
- JSON 模式。
- 连接测试与错误诊断。

API Key 应以受限方式保存在本地，不得写入导出的项目数据、日志或前端调试输出。

#### 翻译设置

- 最大并发请求数。
- 单批字符上限。
- 单批条目上限。
- 失败重试次数。
- 重试退避策略。
- 术语注入策略。
- 额外系统提示词和用户提示词。
- 超长文本处理策略。
- 请求失败后是否自动继续处理其他批次。

配置项必须进行输入校验，对越界数值、空 URL、无效配置等提供明确反馈。

### 6. 断点续传与本地持久化

- 自动保存项目数据、术语表、翻译结果和任务进度。
- 重启应用后，可以恢复项目及上次任务的执行状态。
- 中断任务后，确保已完成的批次不会因为重启或继续执行而重复处理。
- 关键文件采用临时文件写入后原子替换的方式，降低写入过程中数据损坏的风险。
- 对保存失败、工作区损坏及版本不兼容提供错误提示和恢复策略。

## 三、Material UI 开发规范

### 1. 组件使用

- 所有界面统一使用 Material UI 组件。
- 根据实际需求优先选用 `Button`、`IconButton`、`TextField`、`Select`、`MenuItem`、`Switch`、`Checkbox`、`Dialog`、`Drawer`、`Tabs`、`Table`、`Paper`、`Card`、`Chip`、`Tooltip`、`Alert`、`Snackbar`、`LinearProgress`、`CircularProgress`、`Skeleton` 等组件。
- 对数据表格优先使用 MUI `Table` 及相关组件。只有在确有复杂表格能力需求时，才评估引入额外的数据表格依赖。
- 使用 `@mui/icons-material` 提供的图标，不使用 emoji 替代常规操作图标。
- 图标按钮必须具有明确的 `aria-label` 或可访问名称。
- 避免为简单需求重复封装 MUI 已提供的基础组件。

### 2. 主题与样式

- 使用统一的 `createTheme` 创建全局主题，通过 `ThemeProvider` 注入应用。
- 主题负责统一管理色彩、字体、间距、圆角、阴影、组件默认属性和组件样式。
- 使用 MUI 的 `sx` 属性处理局部布局与样式，使用主题的 `components` 配置管理组件的全局默认值和覆盖样式。
- 不为普通组件添加大量独立 CSS 文件，不使用散落的硬编码颜色覆盖主题。
- 自定义样式优先引用 `theme.palette`、`theme.spacing`、`theme.shape` 和 `theme.typography`。
- 支持浅色、深色和跟随系统三种主题模式。
- 用户选择的主色和密度模式应统一作用于各页面、对话框、菜单、表单及提示信息。
- 确保切换主题时，文字、边框、输入框、表格、弹窗、进度条和日志区域都有足够的视觉对比度。
- 紧凑模式应统一调整组件高度、表格行高、控件间距等，不应仅缩小字体。

### 3. 交互规范

- 异步操作必须有清晰的加载、成功、失败及取消状态。
- 危险操作（如删除术语、清空结果、从头执行）应根据影响程度使用确认对话框。
- 长时间任务应展示真实的执行进度，不使用虚构的进度动画代替实际状态。
- 表单提供字段级校验、错误提示及合理的默认值。
- 空列表、无搜索结果、无项目、加载失败等场景必须有明确的空状态。
- 支持键盘导航、可见焦点、适当的 ARIA 属性和合理的对比度。
- 避免无意义的弹窗嵌套，优先使用内联反馈、`Alert` 或 `Snackbar`。
- 日志区域应支持滚动、自动跟随最新记录以及暂停自动滚动。

### 4. 中文桌面应用体验

- 界面默认使用简体中文。
- 采用清晰的桌面工具布局，重点突出任务状态、主要操作和长文本处理效率。
- 导航、表单、按钮、数据表格、对话框和设置项的视觉规范保持一致。
- 原文、译文及日志内容应支持长文本显示，避免过度截断。
- 保证窗口尺寸变化时布局合理，不出现按钮被遮挡、表格溢出或弹窗超出可视区域等问题。

## 五、开发要求

- 严格使用 TypeScript，避免随意使用 `any`。
- Rust 负责文件读写、JSON 处理、任务执行、AI 请求和持久化等核心业务。
- React 页面负责界面展示和交互，通过封装后的 API 与后端通信。
- Zustand 用于跨页面共享的项目、任务、设置等状态；局部表单状态优先保留在组件内。
- 将任务状态、任务进度、任务事件和取消逻辑定义为明确的数据结构，避免依赖界面文本判断业务状态。
- 前后端共用的类型结构应保持一致，新增或变更命令时同步更新 TypeScript 类型及 Mock 实现。
- 在浏览器环境中检测 Tauri API 是否可用；不可用时使用 Mock API，不应因为缺少 Tauri Runtime 导致页面无法预览。
- 任务执行、状态保存、取消和恢复逻辑不得依赖 React 组件是否仍然挂载。
- 避免长时间任务因页面切换、组件重渲染或 Strict Mode 开发行为而意外重复启动。
- 不在前端存储或日志中泄露 API Key。
- 对网络异常、接口返回异常 JSON、批次失败、文件读写失败和用户取消等场景提供可恢复的处理方式。
- 不添加未被需求明确要求的后端框架或大型依赖。

## 六、开发与构建

环境要求：Node.js 20+、Rust 1.85+；Windows 需安装 WebView2 Runtime，Windows 11 通常已自带。

```bash
npm install

# 启动 Tauri 桌面开发环境
npm run tauri dev

# 构建桌面安装程序
npm run tauri build

# 仅启动前端，使用 Mock API
npm run dev

# 检查 TypeScript 类型
npx tsc --noEmit
```

在实际创建项目时，应确认 `package.json` 中存在对应脚本；缺失时补齐，而不是假设脚本必然存在。

## 七、使用流程

1. 打开应用，选择或拖入 `FunnyGameTranslations.json`。
2. 在「翻译配置」中确认语言、文件信息和参考术语表。
3. 进入「术语表收集」，执行收集并检查、修订结果。
4. 进入「翻译任务」，启动批量翻译，查看进度和失败日志。
5. 按需手动修订译文、导入已有译文或继续执行失败任务。
6. 导出译文 JSON，并确认其结构符合游戏读取要求。
7. 需要重新翻译时，通过「从头执行」保留旧译文作为参考并重新生成结果。

## 八、数据格式

### 1. 源文件与译文导出

```json
[
  {
    "id": "dataActors",
    "translations": [
      {
        "original": "佐伯",
        "original_sequence": ["佐伯"],
        "translation_sequence": ["佐伯"]
      }
    ]
  }
]
```

导出的 JSON 必须保留源文件的整体结构、分组关系、条目顺序和原始字段。`translation_sequence` 为译文分段，必须符合游戏预期的数据格式。

### 2. 术语表导入与导出

```json
{
  "terms": [
    {
      "source": "佐伯",
      "target": "佐伯",
      "note": "角色"
    },
    {
      "source": "回復薬",
      "target": "回复药",
      "note": "道具"
    }
  ]
}
```

兼容纯数组及 `original`、`translation` 等常见别名。导入时应先解析并校验，再按照明确的合并规则更新术语表，避免无效文件造成数据损坏。

## 九、数据存放位置

数据目录位于 **exe 同目录下的 `com.funnygameplayer.translator/`**（绿色版可直接整体拷贝）；若程序目录不可写，则回退到系统数据目录 `%APPDATA%/com.funnygameplayer.translator/`。

- 全局设置：`<exe 目录>/com.funnygameplayer.translator/settings.json`
- 项目工作区：`<exe 目录>/com.funnygameplayer.translator/workspaces/<文件名>-<路径哈希>/`
  - `project.json`：项目条目、译文与翻译状态。
  - `glossary.json`：术语表。
  - `glossary_progress.json`：已完成术语收集的分组。
- 最近项目：`<exe 目录>/com.funnygameplayer.translator/recent.json`

首次切换到程序目录时，会把旧的 `%APPDATA%/com.funnygameplayer.translator` 数据复制过来（已存在的文件不覆盖）。

## 十、关键实现要求

### 1. 批次切分

- 同时考虑单批字符上限和单批条目上限。
- 超长条目的处理方式必须可追踪。
- 对超过正常上限 6 倍的超长文本（例如嵌入 JSON 的文本），默认跳过并标记为失败，允许用户在修正配置后重新执行。
- 批次划分应稳定，方便断点续传、问题定位和失败重试。

### 2. 并发与数据一致性

- 每个任务拥有独立的取消令牌。
- 项目数据、术语表及任务状态通过明确的锁或事务式更新策略进行保护。
- 进度计数应由可靠的任务状态机维护，而不是依赖前端计数器自行累加。
- 自动保存由独立任务触发，并使用临时文件加原子替换。
- 避免并发任务同时写入时产生覆盖、丢失更新或损坏的 JSON。

### 3. 失败重试

- 网络错误、超时、限流及可恢复的响应解析错误，按照设置的重试策略进行退避重试。
- 区分可重试错误和不可重试错误。
- 仍然失败的批次需记录错误原因，并可通过「继续执行」重新处理。
- 对 HTTP 错误响应保留安全、必要的诊断信息，不记录敏感凭据。

### 4. 术语注入

- 每个批次仅注入该批次原文中命中的术语。
- 明确处理术语重复、大小写、子串匹配和冲突译名。
- 术语注入策略应兼顾译名一致性与 Token 开销。
- AI 返回结果应校验条目对应关系和预期结构，防止错位覆盖。

### 5. 中断与恢复

- 中断后取消尚未发出的请求，并尽可能取消在途请求。
- 等待在途任务完成清理和状态落盘后，将任务状态更新为「已中断」。
- 继续执行时，根据持久化状态恢复待处理批次，并避免重复计入已完成条目。
- 从头执行应创建明确的新一轮任务状态，同时保留旧译文参考；新旧任务数据之间不得出现竞争写入。
- 明确区分「待处理」「执行中」「已完成」「失败」「已中断」等状态，并定义各状态之间合法的转换规则。

## 十一、验收标准

1. 前端不再使用 Ant Design 组件、样式或主题配置，统一采用 Material UI。
2. 浅色、深色、跟随系统、主题色和紧凑模式均可正常工作，并能在重启后恢复。
3. 欢迎界面能够导入 JSON、解析文件并恢复最近项目。
4. 术语收集和翻译任务能够执行、中断、继续和从头执行。
5. 手动修改的术语和译文能够自动保存，且不会被并发任务静默覆盖。
6. 请求失败、超时、取消和应用重启后，任务状态及进度保持一致。
7. 术语表与译文的导入、导出符合定义的数据格式。
8. 浏览器 Mock 环境可用于调试全部主要页面和典型交互。
