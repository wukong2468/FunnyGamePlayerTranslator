# SourceParser：源文件、术语表与译文的数据处理说明

本文说明三件事：

1. `FunnyGameTranslations.json` 加载成项目时到底做了什么；
2. 项目的术语表是什么结构，导入/导出各做了什么；
3. 项目的译文是什么结构，导入/导出各做了什么。

文中所有示例都来自真实数据结构，并逐条说明每一步对数据做了什么。

---

## 0. 数据流总览

```
FunnyGameTranslations.json ──parse──┐
                                    ├─> Project（内存）──persist──> workspaces/<名称>-<哈希>/project.json
译文 JSON ──import_translations─────┘                              ├─> glossary.json（术语表）
                                                                   ├─> glossary_progress.json（术语收集进度）
                                                                   └─> meta.json（列表摘要）
Project ──export_value──> 译文 JSON（结构与源文件一致，可回填）
Glossary ──export_file──> 术语表 JSON
```

- 源文件只在「首次打开」和「选择重新加载」时被解析；之后项目完整数据都存在工作区里，源文件删除也能继续工作。
- 工作区目录名：`<源文件名主干>-<源文件路径 SHA-256 前 16 位>`（64 位），例如 `FunnyGameTranslations-b1f5cdbe9c3a4f27`。
  - 升级前创建的旧工作区使用 8 位哈希名，仍会继续沿用，不会丢进度；
  - 万一目录已存在但归属的是另一个源文件（哈希冲突），会自动改用完整哈希（64 位十六进制）目录兜底，不会让两个文件共用同一个项目。

## 1. 从 FunnyGameTranslations.json 加载到项目

入口：`AppState::open_project(source_path, reload_source)`（`src-tauri/src/state.rs`）。

### 1.1 处理步骤

| 步骤 | 做什么 |
| --- | --- |
| 1 | 由源文件路径算出工作区目录，必要时创建 |
| 2 | 读取文件文本，去掉 UTF-8 BOM |
| 3 | 解析 JSON 结构（见 1.2） |
| 4 | 每个分组、每个条目扁平化成内部模型 `Group / TextItem` |
| 5 | 若工作区已有 `project.json`，按「分组 id + 组内序号 + 原文一致」把上次的译文/状态合并进来 |
| 6 | `normalize_statuses()`：原文没有字母的条目统一置为「无需翻译」 |
| 7 | 计算源文件 SHA-256，记到 `project.sourceHash`（用于下次判断源文件是否被改动） |
| 8 | 立即落盘：`project.json`（完整副本）+ `meta.json`（列表摘要） |
| 9 | 读取 `glossary.json`、`glossary_progress.json`，并清理已不存在分组留下的收集记录 |
| 10 | 按 `job` 快照恢复任务进度显示 |

### 1.2 JSON 结构的兼容规则

- 顶层可以是**数组**，也可以是**对象**：对象取 `groups` 字段，同时兼容别名 `data`。
- 分组字段：`translations` 或 `items`（二选一），缺失报错「第 N 个分组缺少 translations 数组」。
- 分组 `id` 缺失或为空 → 自动命名为 `group{索引}`（0 开始，如 `group0`）。
- 条目字段：
  - `original_sequence`：多段原文；为空时用 `[original]`。
  - `translation_sequence`：多段译文；为空时**默认等于原文**（视为未翻译）；段数与原文不一致时整体拼成一段。
  - `original`：为空时用 `original_sequence` 拼回来的文本。
- **未识别字段不丢弃**：分组上除 `id/translations/items` 之外的字段、条目上除 `original/original_sequence/translation_sequence/status/error/reference` 之外的字段，会存进 `extra`，导出时原样写回。
- 文件为空数组报错「文件中没有任何翻译分组」；条目总数为 0 报错「文件不包含任何文本条目」。

### 1.3 条目状态判定

| 条件 | 状态 | 含义 |
| --- | --- | --- |
| 原文全为空，或原文不含任何字母（纯数字/符号） | `skipped` | 无需翻译，不计入翻译进度 |
| `translation_sequence` 非空且与原文不同 | `done` | 已翻译 |
| 其余（含「译文 = 原文」） | `pending` | 待处理 |

### 1.4 举例：源文件 → 项目

源文件 `FunnyGameTranslations.json`：

```json
[
  {
    "id": "dataActors",
    "note": "保留未知字段",
    "translations": [
      {"original": "佐伯", "original_sequence": ["佐伯"], "translation_sequence": ["佐伯"], "no": 1},
      {"original": "回復薬", "original_sequence": ["回復薬"], "translation_sequence": ["回复药"]},
      {"original": "複数行", "original_sequence": ["一行目", "二行目"], "translation_sequence": ["第一行", "第二行"]},
      {"original": "1234", "original_sequence": ["1234"]}
    ]
  },
  {
    "id": "dataEnemies",
    "items": [
      {"original": "スライム", "translation_sequence": ["史莱姆"]}
    ]
  }
]
```

解析后得到 2 个分组、5 个条目：

| 分组 | # | sourceSegments | targetSegments | 状态 | 说明 |
| --- | --- | --- | --- | --- | --- |
| dataActors | 0 | `["佐伯"]` | `["佐伯"]` | pending | 译文与原文相同 → 视为未翻译 |
| dataActors | 1 | `["回復薬"]` | `["回复药"]` | done | 已有译文 |
| dataActors | 2 | `["一行目","二行目"]` | `["第一行","第二行"]` | done | 段数一致，保持数组结构 |
| dataActors | 3 | `["1234"]` | `["1234"]` | skipped | 不含字母，无需翻译 |
| dataEnemies | 0 | `["スライム"]` | `["史莱姆"]` | done | 分组用 `items` 字段、条目无 `original_sequence`，自动补成单段 |

额外数据处理：

- 分组 `dataActors` 的 `note` 字段 → `Group.extra = { "note": "保留未知字段" }`；
- 条目 0 的 `no: 1` → `TextItem.extra = { "no": 1 }`；
- 两者在导出时原样写回，所以「导入 → 导出」不会丢字段。

落盘后的 `project.json` 片段（内部结构，含更多状态字段）：

```json
{
    "version": 1,
    "sourceHash": "b6f3…",
    "sourcePath": "D:\\…\\FunnyGameTranslations.json",
    "fileName": "FunnyGameTranslations.json",
    "sourceLang": "ja",
    "targetLang": "zh-CN",
    "groups": [
        {
            "id": "dataActors",
            "items": [
                {
                    "original": "佐伯",
                    "sourceSegments": ["佐伯"],
                    "targetSegments": ["佐伯"],
                    "status": "pending",
                    "no": 1
                }
            ],
            "note": "保留未知字段"
        }
    ],
    "job": { "phase": "idle", "total": 0, "done": 0, "failed": 0, "message": "" }
}
```

### 1.5 与上次进度合并（再次打开同一文件）

规则：按 **分组 id + 组内序号** 找到旧条目，且 **原文完全一致** 才覆盖译文与状态。

举例：上次 `project.json` 中 `dataActors#1` 是「回復薬 → 回复药」，本次源文件这一条被改成「回復薬A」：

| 情况 | 结果 |
| --- | --- |
| 原文仍是「回復薬」 | 沿用旧译文「回复药」和状态 `done` |
| 原文变成「回復薬A」 | 不匹配，保留本次源文件给出的状态（这里是 `pending`），旧译文不迁移 |

合并还会沿用上次的语言设置（`sourceLang/targetLang`）与任务进度快照（`job`）。

### 1.6 重新加载（源文件被修改后）

前端在打开项目前调用 `project_source_status`：把源文件当前 SHA-256 与 `project.sourceHash` 比对，不一致就弹窗询问。

- **不重新加载**：沿用工作区副本（哈希不更新，下次仍会提示）。
- **重新加载**：以源文件为准重建条目，规则见 `Project::apply_reload_from`：

| 旧条目状态 | 重新加载后 |
| --- | --- |
| 原文未变且 `done` | **保留译文**（分段数必须与原文一致），人工标记 `manual` 一并保留 |
| `pending` / `failed` / 超长跳过 | 重置为目标=原文，状态回到 `pending`（无字母则 `skipped`） |
| 源文件中已不存在该条目 | 条目连同原文、译文一起删除 |

举例：

- 旧项目：`dataActors` 有 4 条（0 佐伯 pending、1 回復薬 done、2 複数行 done、3 1234 skipped）。
- 新源文件：删掉了第 2 条 `複数行`，其余不变。
- 结果：`dataActors` 只剩 3 条；0 仍 pending；1 仍 done 且保留「回复药」；3 仍 skipped；`複数行` 的原文与译文都被丢弃。
- 术语表、术语收集进度不受影响；`project.job` 重置为 idle。

同项目已在打开状态时，只有 `reload_source = true` 才会真正重新加载；否则直接返回提示「该文件已在当前项目中打开，未重复加载」。

## 2. 术语表

### 2.1 存储结构

文件：`<工作区>/glossary.json`

```json
{
    "terms": [
        { "source": "佐伯", "target": "沙伯", "note": "角色", "manual": true },
        { "source": "根岸", "target": "", "note": "角色", "manual": false },
        { "source": "ダンジョン", "target": "迷宫", "note": "地点", "manual": false }
    ]
}
```

字段含义：

| 字段 | 说明 |
| --- | --- |
| `source` | 原文术语，去空格后不能为空，且不超过 120 字符 |
| `target` | 译名，空表示「已知术语但还没有译名」 |
| `note` | 备注，多为分类（角色/地点/道具…） |
| `manual` | `true` = 人工维护（手工新增、编辑、导入），AI 不会覆盖；`false` = AI 抽取 |

- 运行时的索引（`index`、`by_char`）只在内存里，不落盘。
- 去重键：`source.trim().toLowerCase()`；同名术语只保留一条。
- AI 抽取合并（`merge_ai_term`）：已存在则**只补空译名**，绝不覆盖已有译名。

### 2.2 导出术语表

入口：`export_glossary` → `Glossary::export_file`。

- 只导出三个字段：`source`、`target`、`note`（**不导出 `manual`**）。
- 结构：`{ "terms": [ … ] }`，4 空格缩进，原子写入（临时文件 + rename）。

以上面的术语表为例，导出结果：

```json
{
    "terms": [
        {
            "source": "佐伯",
            "target": "沙伯",
            "note": "角色"
        },
        {
            "source": "根岸",
            "target": "",
            "note": "角色"
        },
        {
            "source": "ダンジョン",
            "target": "迷宫",
            "note": "地点"
        }
    ]
}
```

注意：未翻译的术语也会导出（`target` 为空字符串），再次导入时它只会补全译名。

### 2.3 导入术语表

入口：`import_glossary(path, mode)` → `Glossary::import_file`，`mode` 为 `merge`（合并）或 `replace`（替换）。

**结构兼容**

- 顶层：纯数组 `[…]`；或对象中含 `terms` / `glossary` / `items` / `data` 数组；或对象里第一个数组字段。
- 元素：对象或字符串。
  - 字符串（如 `"ドラゴン"`）视为「只有原文」的术语，译名为空。
  - 对象字段别名：
    - 原文：`source` / `original` / `src` / `term` / `原文`
    - 译名：`target` / `translation` / `dst` / `translated` / `译文`
    - 备注：`note` / `remark` / `comment` / `desc` / `备注`

**逐条处理规则**

| 情况 | 结果 |
| --- | --- |
| 原文清洗后为空，或超过 120 字符 | `skipped` |
| 同一个导入文件里原文重复（忽略大小写） | 后出现的 `skipped` |
| 当前术语表已有该原文（忽略大小写），且 `target`、`note` 完全相同 | `skipped` |
| 已有条目是人工维护且有译名，导入项也带译名 | **保留旧译名**，记入 `conflicts`（最多 20 条），`skipped` |
| 已有条目可更新 | 导入项有译名则覆盖译名；有备注则覆盖备注；`manual` 置为 `true`，`updated` |
| 不存在该原文 | 追加，`manual = true`，`added` |

`replace` 模式会**先清空**现有术语表再逐条导入（规则同上，只是没有「已存在」分支）。

**举例**

当前术语表（初始状态）：

```json
{
    "terms": [
        { "source": "佐伯", "target": "沙伯", "note": "角色", "manual": true },
        { "source": "根岸", "target": "", "note": "角色", "manual": false },
        { "source": "ダンジョン", "target": "迷宫", "note": "地点", "manual": false }
    ]
}
```

导入文件 `merge` 模式：

```json
{
    "terms": [
        { "original": "佐伯", "translation": "佐伯", "remark": "角色" },
        { "source": "根岸", "target": "根岸" },
        "ドラゴン",
        { "src": "ダンジョン", "dst": "地牢" },
        { "source": "   ", "target": "空原文" },
        { "source": "佐伯", "target": "重复项" }
    ]
}
```

逐条结果：

| # | 导入项（规范化后） | 处理 | 结果 |
| --- | --- | --- | --- |
| 1 | 佐伯 → 佐伯 | 已有条目、人工且有译名「沙伯」 | 冲突，保留「沙伯」，`skipped` |
| 2 | 根岸 → 根岸 | 已有条目、译名为空 | 补译名「根岸」，`manual=true`，`updated` |
| 3 | ドラゴン（译名为空） | 不存在 | 新增，`manual=true`，`added` |
| 4 | ダンジョン → 地牢 | 已有条目、非人工 | 覆盖译名为「地牢」，保留原备注，`manual=true`，`updated` |
| 5 | 空白原文 | 清洗后为空 | `skipped` |
| 6 | 佐伯 → 重复项 | 与第 1 项同一原文（文件内重复） | `skipped` |

返回的统计（`GlossaryImportReport`）：

```json
{
    "total": 6,
    "added": 1,
    "updated": 2,
    "skipped": 3,
    "replaced": false,
    "conflicts": ["佐伯：保留“沙伯”，忽略导入的“佐伯”"],
    "termsTotal": 4
}
```

导入后的术语表：

```json
{
    "terms": [
        { "source": "佐伯", "target": "沙伯", "note": "角色", "manual": true },
        { "source": "根岸", "target": "根岸", "note": "角色", "manual": true },
        { "source": "ダンジョン", "target": "地牢", "note": "地点", "manual": true },
        { "source": "ドラゴン", "target": "", "note": "", "manual": true }
    ]
}
```

同一条目在 `replace` 模式下：先清空，再全部按「新增」处理，`replaced = true`，因此 `conflicts` 为空。

### 2.4 翻译时如何使用术语表

`Glossary::matches_for(text)`：

- 只取有译名的术语；
- 大小写不敏感地匹配「原文出现在待翻译文本中」；
- 按原文长度**从长到短**排序（避免短词覆盖长词），最多注入 40 条；
- 是否注入由设置项「术语注入策略」决定（不注入 / 仅命中 / 命中并带备注）。

## 3. 译文

### 3.1 内部结构

`project.json` 中每个条目（`TextItem`）：

```json
{
    "original": "一行目\n二行目",
    "sourceSegments": ["一行目", "二行目"],
    "targetSegments": ["第一行", "第二行"],
    "status": "done",
    "error": null,
    "reference": null,
    "skipped": false,
    "manual": false,
    "no": 1
}
```

| 字段 | 说明 |
| --- | --- |
| `original` | 完整原文（多段以换行拼接），用于展示与导入校验 |
| `sourceSegments` | 分段原文，翻译时按段对齐 |
| `targetSegments` | 分段译文；未翻译时等于 `sourceSegments` |
| `status` | `pending` / `done` / `failed` / `skipped` |
| `error` | 失败原因（成功或未处理时为 `null`） |
| `reference` | 「从头执行」时保留的旧译文，仅作为模型参考 |
| `skipped` | 是否因超长被跳过 |
| `manual` | 人工编辑或导入的译文，AI 不覆盖 |
| `extra` | 源文件里的其他字段，导出时原样带回 |

### 3.2 导出译文

入口：`export_translation(dest_path)`。

- 先 `persist_session()` 把当前进度落盘，再生成 JSON；
- 结构与源文件一致：顶层数组，每项 `{ id, translations: [...] }`；
- 每个条目固定写 `original`、`original_sequence`、`translation_sequence`，再补回 `extra` 里的未知字段（不会覆盖上面三个字段）；
- 4 空格缩进，原子写入；`status/error/reference/manual` 等内部字段**不导出**。

假设在 1.4 的项目基础上把「佐伯」改成了「沙伯」，导出结果：

```json
[
    {
        "id": "dataActors",
        "note": "保留未知字段",
        "translations": [
            {
                "original": "佐伯",
                "original_sequence": ["佐伯"],
                "translation_sequence": ["沙伯"],
                "no": 1
            },
            {
                "original": "回復薬",
                "original_sequence": ["回復薬"],
                "translation_sequence": ["回复药"]
            },
            {
                "original": "複数行",
                "original_sequence": ["一行目", "二行目"],
                "translation_sequence": ["第一行", "第二行"]
            },
            {
                "original": "1234",
                "original_sequence": ["1234"],
                "translation_sequence": ["1234"]
            }
        ]
    },
    {
        "id": "dataEnemies",
        "items": [
            {
                "original": "スライム",
                "original_sequence": ["スライム"],
                "translation_sequence": ["史莱姆"]
            }
        ]
    }
]
```

几点说明：

- `dataActors` 的 `note`、条目的 `no` 原样保留（导出时 `extra` 只是补字段）。
- 未翻译/失败/无需翻译的条目也会导出，`translation_sequence` 就是原文（游戏里回填等于没翻译）。
- 源文件用的是 `items` 字段时，导出统一写成 `translations`（两者解析时等价）。

### 3.3 导入译文

入口：`import_translations(path)` → `Project::import_translations`。

**定位规则**

1. 分组按 `id` 匹配；同一 id 在项目里出现多次时，按出现顺序依次消费导入文件中的同名分组。
2. 组内条目按**序号**对应（第 N 条对第 N 条），不会新增或删除条目。
3. 原文校验：导入条目的 `original_sequence`（缺省用 `[original]`）必须与项目条目 `sourceSegments` 相同；若不同，还允许 `original` 字符串与项目 `original` 相同（兼容只给一段的写法），否则记为 `mismatched` 并跳过。

**逐条处理**

| 情况 | 结果 |
| --- | --- |
| 分组 id 在项目里不存在 | `unknownGroups += 1` |
| 导入条目序号超出该组条目数 | `skipped += 1` |
| `translation_sequence` 为空 | `skipped += 1` |
| 译文清洗后为空 | `skipped += 1` |
| 原文对不上 | `mismatched += 1` |
| 正常 | 写入译文，`status = done`，`manual = true`（AI 不再覆盖），`applied += 1` |
| 写入后译文与原文完全相同 | 视为未翻译：状态回到 `pending`（无字母则 `skipped`），`manual = false` |

**举例**

项目当前状态：

| 分组 | # | 原文 | 状态 |
| --- | --- | --- | --- |
| dataActors | 0 | 佐伯 | pending |
| dataActors | 1 | 回復薬 | pending |
| dataActors | 2 | 一行目 / 二行目 | pending |
| dataEnemies | 0 | スライム | pending |

导入文件：

```json
[
  {
    "id": "dataActors",
    "translations": [
```

### 3.4 段数与原文对不上的处理

导入的 `translation_sequence` 段数与原文段数不一致时（例如原文 2 段、译文 1 段）：

- 全部译文拼成一段，放进第一段；
- 其余段留空，保证 `targetSegments` 长度始终等于 `sourceSegments` 长度，避免后续导出时结构与原文错位。

### 3.5 导入 / 导出 / 重新加载的关系

| 操作 | 是否改条目结构 | 是否改译文 | 备注 |
| --- | --- | --- | --- |
| 导入译文 | 否（只按位置覆盖） | 覆盖匹配到的条目 | 不新增、不删除 |
| 导出译文 | 否 | 否 | 内部状态字段不导出 |
| 重新加载源文件 | 是（以源文件为准） | 保留原文未变的 `done` 译文，其余重置 | 源文件缺失的条目会被删除 |
| 从头执行翻译 | 否 | 全部重置为待处理，旧译文转为 `reference` 参考 | 术语表不变 |

## 4. 常见问题

**Q：为什么导入后「已完成」数没变？**
A：导入的译文若与原文完全相同，会被判定为「未翻译」，状态回到 `pending`。

**Q：源文件删除了还能打开项目吗？**
A：可以。项目完整数据在 `project.json`；打开时若源文件不存在，直接用副本，并提示「源文件已不存在，已使用项目内保存的完整副本」。

**Q：重新加载会不会丢术语表？**
A：不会。术语表与术语收集进度是独立文件，重新加载只处理项目条目；仅「原文未变且已完成」的译文会被保留，其余条目重置。

**Q：为什么导出文件里多了 `note`、`no` 这些字段？**
A：解析时它们被存进 `extra`，导出时原样补回，保证「源文件 → 项目 → 导出」不丢字段。
